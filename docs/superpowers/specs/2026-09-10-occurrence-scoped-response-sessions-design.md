# Occurrence-Scoped Response Sessions Design

**Date:** 2026-09-10
**Status:** Approved roadmap slice for local implementation
**Parent roadmap:** `LEAI/docs/product-strategy/2026-08-20-question-set-wizard-feature-roadmap.md`, Step 2

## Goal

Give every newly persisted student chat message an authoritative path through one anonymous response session to one exact `FeedbackGPT` survey occurrence and its course, while preserving all legacy fields and read contracts during migration.

## Scope

This slice is deliberately additive:

- add `ResponseSession` with a server-generated UUID public identifier;
- scope the client-provided anonymous session identifier by survey, not globally;
- attach new API-written `FeedbackMessage` rows to that session;
- allocate a unique, server-side message sequence within each response session;
- retain `FeedbackMessage.session_id`, `student_id`, `gpt_id`, and existing API payloads for compatibility;
- keep historical rows valid with nullable new relationships;
- add no data backfill and perform no production migration or cutover.

This slice does not add stable recurring links, survey series, immutable question-set revisions, preview data, named students, cross-week pseudonyms, or research telemetry. It also does not change instructor-facing analysis reads yet.

## Data model

### `ResponseSession`

- `public_id`: server-generated UUID, unique and immutable in normal application flows.
- `course`: required protected relationship to the course.
- `survey`: required cascading relationship to the exact `FeedbackGPT` occurrence. Survey deletion currently deletes its response data, so this slice preserves that behavior.
- `client_session_id`: the existing anonymous browser/session identifier.
- `source`: `student` for this slice; `pdf` is reserved for the later controlled backfill/import path.
- `started_at`: creation timestamp, currently defined as first successful message persistence.
- `completed_at`: nullable lifecycle seam; no completion transition is introduced in this slice.
- `next_message_sequence`: transactionally allocated one-based sequence counter.

The database enforces unique `(survey, client_session_id)`. The same client identifier may therefore appear in multiple survey occurrences without conflating those occurrences.

Application validation requires `ResponseSession.course == ResponseSession.survey.course`. New writes reject surveys without a course.

### `FeedbackMessage`

- `response_session`: nullable cascading foreign key during the additive migration period.
- `sequence`: nullable positive integer.

Legacy rows remain valid with both fields null. New student API writes set both. A check constraint requires the pair to be either both null or both populated, and a unique constraint prevents duplicate sequence numbers within one response session.

## Write service

Create `datapipeline/response_sessions.py` as the transaction owner. Its public interface is:

```python
persist_feedback_messages(payloads: list[dict]) -> list[FeedbackMessage]
```

The service validates the complete batch before writing, resolves every referenced survey, rejects missing or course-less surveys, resolves or creates one response session per `(survey, client_session_id)`, locks sessions in deterministic order, allocates contiguous sequence ranges, and bulk-creates messages atomically. Any invalid item rejects the whole batch and reports its input index.

The service accepts the current student-message payload, including form attribution and consent/referral fields. It derives course and response-session ownership from `gpt_id`; it never trusts a client-supplied course identifier.

## Endpoint compatibility

`feedback_message_api` and `feedback_messages_bulk_api` retain their URLs, request shapes, success status, and existing success fields. They add response-session metadata to successful responses. The single endpoint returns `response_session_id` and `sequence`; the bulk endpoint returns `response_sessions` and `saved`.

For these student response endpoints, `gpt_id` becomes required because an authoritative occurrence cannot be derived without it. The current LEAI student and CSV-import clients already send `gpt_id`.

Direct ORM writes used by historical fixtures and controlled PDF code remain compatible and may leave the new fields null until their own migration slice.

## Failure and privacy behavior

- malformed JSON, missing fields, unknown surveys, overlong client session IDs, and surveys without a course return HTTP 400 with no rows written;
- unexpected persistence failures return HTTP 500 without exposing database details;
- no student account, email, device key, fingerprint, IP address, or new behavioral event is collected;
- the response-session UUID is generated by the server and is not derived from student content.

## Migration safety

Migration `0047` is schema-only. It creates the new table, nullable message fields, indexes, and constraints. It contains no `RunPython`, no inference from names or timestamps, and no mutation of existing `FeedbackMessage`, `FeedbackGPT`, certificate, team, banner, or identity rows.

Historical inventory, quarantine, idempotent backfill, dual-read parity, and read cutover remain separate reviewed milestones.

## Acceptance criteria

1. Two messages for the same `(survey, client_session_id)` share one response session and receive sequences 1 and 2.
2. The same client identifier used for two surveys creates two response sessions.
3. A new message has an authoritative `message → response session → survey → course` path.
4. Invalid items make a bulk write atomic: zero messages, sessions, and counter increments persist.
5. Legacy direct message creation remains valid with null normalized fields.
6. The migration plan is additive and `makemigrations --check --dry-run` reports no drift.
7. The complete backend test suite remains green.
